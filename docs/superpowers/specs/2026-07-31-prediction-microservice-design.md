# 予測配信マイクロサービス 設計書

**作成日:** 2026-07-31
**目的:** マイクロサービスアーキテクチャの学習。予測配信（推論）を独立プロセスとして切り出し、段階的に移行できる仕組みを作る。

---

## 背景と動機

StockFixer は現在モジュラーモノリス（`src/` 配下の Bounded Context による論理分離）として動いている。一人運用・単一ホスト・単一 Postgres という規模では、この構成は合理的である。

一方で「マイクロサービスの仕組みを学びたい」「今後少しずつ移行できる形にしたい」という動機から、Bounded Context のうち1つ（予測配信）を独立サービスとして切り出す実験を行う。

### なぜ予測配信を選んだか

- 入力（特徴量・現在価格）と出力（予測価格）が明確で、境界を引きやすい
- 計算主体であり、状態を持たない（ステートレス）
- 失敗してもフォールバックで従来経路に戻せるため、本番リスクを最小化できる

## 全体構成

```
┌─────────────────────────────────────┐
│ StockFixer 本体（モノリス）              │
│                                     │
│  scheduler → prediction_pipeline    │
│      ↓                              │
│  ① load_stock_features() でDB読み    │
│  ② yfinanceで現在価格取得              │
│  ③ ────HTTP POST /predict────→      │
│  ④ 返ってきた予測をDBへ保存             │
└─────────────────────────────────────┘
                  ↓ HTTP
┌─────────────────────────────────────┐
│ 推論サービス（新規・独立プロセス）          │
│  POST /predict                      │
│   入力: 特徴量1行 + 現在価格 + モデル名   │
│   処理: モデルロード → 特徴量アライン →   │
│         推論 → アンサンブル             │
│   出力: 予測価格・変化率・使用モデル数     │
│                                     │
│  DB接続なし / yfinance接続なし          │
│  GET /health                        │
└─────────────────────────────────────┘
```

### 責務の分割

| 担当 | 責務 |
|---|---|
| 本体 | データ取得（Postgres・yfinance）、モデル重みの算出、予測結果の永続化 |
| 推論サービス | 計算のみ。外部 I/O を一切持たず、モデルファイル（joblib）だけを読む |

### DB アクセス方式の決定: API 経由（共有DB直結ではない）

推論サービスは **Postgres の接続情報を一切持たない**。特徴量もモデル重みも、呼び出し側（本体）が取得して HTTP リクエストのペイロードとして渡す。

共有DB直結（両サービスが同じ Postgres に繋ぐ）方式も検討したが、以下の理由で不採用とした。

- スキーマで密結合したままとなり、「プロセスを分けただけ」になる
- `stock_features` の列を変更すると推論サービスも壊れる
- マイクロサービスが本来教える「サービスは自分のデータだけを持ち、他は必ず API 越し」という境界の引き方が学べない

### サービス境界の決定: 純粋な推論サービス

現行の `predict_with_unified_model()` は、特徴量読み込み・yfinance からの現在価格取得・モデル推論・アンサンブル重み付けを1つの関数内で行っている。このうち **推論とアンサンブルのみ** を切り出す。

- yfinance からの現在価格取得は本体に残す（サービスを外部API依存にしない）
- モデル重みの算出（`model_metrics` テーブル由来）も本体に残す（DB非依存を貫くため）

結果として推論サービスは外部 I/O ゼロとなり、テストが容易で境界が明快になる。

## API コントラクト

### `POST /predict`

リクエスト:

```json
{
  "market": "jp",
  "symbol": "7203",
  "current_price": 2500.0,
  "features": {"Close_lag1": 2480.0, "rsi_lag1": 55.2, "...": 0.0},
  "model_types": ["UnifiedStockXGBoost", "UnifiedStockLightGBM"],
  "model_weights": [0.6, 0.4]
}
```

レスポンス（200）:

```json
{
  "market": "jp",
  "symbol": "7203",
  "current_price": 2500.0,
  "avg_pred_price": 2537.5,
  "diff_ratio": 0.015,
  "model_count": 2,
  "used_models": ["UnifiedStockXGBoost", "UnifiedStockLightGBM"]
}
```

**設計上のポイント:**

- `model_weights` は本体側で計算して渡す。重みは `model_metrics` テーブル（DB）から引くため、推論サービスに DB 接続を持たせない方針の帰結である
- 全モデルの推論が失敗した場合も HTTP 200 を返し、`model_count: 0` で表現する。本体側はこれを見て「予測なし」として扱う（既存の `predict_with_unified_model()` が `None` を返すのと同じ意味）
- `model_weights` の要素数は `model_types` と一致していなければならない（バリデーションエラー時は 422）

**モデルファイルの配置:**

推論サービスは `python/models/` 配下の joblib ファイルを読む。本体と同じディレクトリをマウントして共有する（フェーズ2 で docker-compose に追加する際は read-only マウントとする）。モデルの学習・更新は本体の責務であり、推論サービスは読むだけである。

**特徴量アラインメントの責務:**

現行の `predict_with_unified_model()` が行っている「モデルの `feature_names_in_` に合わせて不足特徴量を 0 で埋め、順序を揃える」処理は **推論サービス側** が担当する。モデルファイルを持っているのがサービス側であり、期待される特徴量名を知っているのもサービス側であるため。本体は DB から読んだ特徴量をそのまま送ればよい。

### `GET /health`

```json
{"status": "ok", "loaded_models": ["UnifiedStockXGBoost"]}
```

モデルがロード可能かを返す。Docker HEALTHCHECK から利用することを想定。

## フォールバック設計

推論サービスが停止している・タイムアウトした・5xx を返した場合、本体は **エラーにせず従来のインプロセス推論にフォールバックする**。

```
PREDICTION_SERVICE_URL 未設定
    → 従来通り本体内で推論（既定動作、既存の挙動と完全に同一）

PREDICTION_SERVICE_URL 設定済み
    → HTTP で推論サービスを呼ぶ
        → 成功: その結果を使う
        → 失敗（接続不可 / タイムアウト / 5xx）:
             警告ログを出してインプロセス推論にフォールバック
```

これはフィーチャーフラグと同じ発想であり、実験用サービスが本番を壊さないための安全弁である。いつでも環境変数を外すだけで元に戻せる。

## ファイル構成

```
python/
  services/                       ← 新規ディレクトリ（本体 src とは分離）
    prediction_service/
      __init__.py
      app.py                      ← FastAPI アプリ（/predict, /health）
      types.py                    ← リクエスト/レスポンスの Pydantic モデル
      inference.py                ← 推論ロジック（モデルロード・アライン・アンサンブル）
      README.md                   ← 起動方法・設計意図（学習メモ）
    Dockerfile.prediction         ← 推論サービス用（本体とは別イメージ）

  requirements-service.txt        ← 推論サービス専用の依存（fastapi, uvicorn）

  src/prediction/
    remote_client.py              ← 新規: 本体からHTTPで呼ぶクライアント＋フォールバック

  tests/unit/services/
    test_prediction_service.py    ← FastAPI TestClient でエンドポイント検証
    test_remote_client.py         ← クライアントのフォールバック挙動検証
```

### なぜ `services/` を `src/` の外に置くか

`src/` 配下は import-linter のレイヤー契約（`api` > `orchestration` > 各BC > `domain`/`infrastructure`/`utils`）に縛られている。推論サービスは「本体とは別にデプロイされる独立プロセス」であり、このレイヤー階層の内側ではなく外側に位置する。`src/` の外に置くことで CI の `import-linter` とも衝突しない。

### なぜ依存を分けるか

`fastapi` / `uvicorn` は推論サービスのみが必要とする。`requirements.txt` に追加すると本体イメージも不必要に肥大化するため、`requirements-service.txt` として分離する（Dockerfile も別のため自然な分割）。

## テスト戦略

| 対象 | 方法 |
|---|---|
| 推論サービス | FastAPI `TestClient` で HTTP 経由の検証。モデルは `MagicMock` を注入し実ファイル不要 |
| クライアント | `requests` をモックし、①正常応答 ②タイムアウト ③サービス 5xx の3ケースでフォールバックが効くことを検証 |
| 既存テスト | 影響ゼロ。`PREDICTION_SERVICE_URL` 未設定が既定のため、既存の予測パスのテストは一切変わらない |

## 段階移行のロードマップ

今回実装するのは **フェーズ1 のみ**。残りは将来の選択肢として設計に織り込んでおく。

| フェーズ | 内容 | 状態 |
|---|---|---|
| **1** | 推論サービス新設＋クライアント（既定OFF・フォールバック付き）。手動で起動して動作確認できる状態まで | **今回のスコープ** |
| 2 | docker-compose に推論サービスを追加し、ローカルで常時起動して検証 | 将来 |
| 3 | 本番で `PREDICTION_SERVICE_URL` を設定し、実際に HTTP 経路へ切り替え | 将来 |
| 4 | 特徴量 API（`GET /features/...`）を追加し、推論サービス側から自律的に取得する形へ発展 | 将来（学習の続き） |

### フェーズ1 の完了条件

- 推論サービスを独立プロセスとして起動でき、`curl` で `POST /predict` を叩くと予測が返る
- `PREDICTION_SERVICE_URL` を設定した状態で本体から呼び出すと、インプロセス推論と同じ結果が得られる
- サービスを停止した状態でも本体は警告ログを出して従来通り動作する（フォールバック確認）
- 既存の全テストが通り、CI が green

---

## スコープ外（意図的に含めないもの）

- **本番切り替え**: 今回はコードを追加するのみで、本番の `.env` や docker-compose は変更しない
- **特徴量 API**: フェーズ4 の題材として残す
- **認証**: 内部通信を想定しているため、フェーズ1 では認証を実装しない（フェーズ3 で本番導入する際に再検討する）
- **複数インスタンス・ロードバランシング**: 学習の焦点ではないため扱わない
