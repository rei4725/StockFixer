# Claude駆動ルール生成・検証パイプライン

## 背景

`src/rule_engine/`（ルールベースシグナル生成）は、人間が書いた6〜7個の固定ルールテンプレート
（`VolumeBreakoutRule` 等）から、銘柄ごとに勝率50%以上・純利益プラスという緩いしきい値で最良の
1つを機械的に選ぶだけの仕組みしか持たない。ルール自体を新しく発想する機構は無い。

一方 `src/backtest/factory.py`（戦略ファクトリー、#369）は、固定パラメータグリッドから乱数で
パラメータを選ぶことで仮説を量産し、DSR/PBO/窓別リターン等の厳格な過学習ガード（#372）を
通過したものだけを人間の昇格判断に回す仕組みを既に持つ。ここには `hypothesis_review.py` という
Claudeレビュー機構もあるが、「読み取り専用の助言のみ、合否判定には一切関与しない」設計であり
既定で無効。

本設計は、この戦略ファクトリーの枠組みに「Claudeが新しいルールのロジック自体（新しいPython
コード）を発想する」という新しい仮説生成源を追加するものである。既存のパラメータ探索型仮説と
異なり、Claude生成コードは任意の実行可能コードであるため、実行安全性・過学習対策・本番反映の
それぞれに新しい設計課題が生じる。

## 目的

- Claudeに新しい `TradingRule` 実装を発想・生成させ、既存の戦略ファクトリーの厳格な過学習ガード
  （DSR/PBO/窓別リターン/#372ガード）をそのまま通過させることで、量と質を両立した候補生成を行う
- 生成コードの実行は完全に隔離されたサンドボックス内で行い、静的検査・実行制限の二段構えで
  安全性を担保する
- 合格した候補は、人間がGitHubの通常PRレビューを経て初めて本番シグナル生成に反映される
  （Claudeは合否判定にも本番反映にも一切関与しない）

## 非目標・スコープ外

- マクロ/クロスアセット特徴量（VIX・ドル円・米10年債等）・センチメント特徴量・他銘柄との
  クロスセクショナルな比較の `generate_signal(df)` への追加 — 既存ML予測パイプラインには
  存在するが、ルールエンジンには配線されていない。本設計のMVPでは既存ルールと同じ入力
  （単一銘柄OHLCV + 技術指標約19列 + 週足/月足マルチタイムフレーム特徴量10列）に留め、
  拡張は将来検討とする（理由: 昇格後の本番シグナル生成にも同じ特徴量を配線し直す必要があり、
  PITずれのリスク面も増えるため、まずは安全な生成パイプライン自体の実証を優先する）
- 実売買の発注ロジック（`trading/brokers/`, `domain/trading_rules.py` 等）の自動変更 — 対象外
- ゲート不合格候補への修正リトライ（詳細は後述） — 意図的に対象外

## 既存ドキュメントとの関係（重要）

`docs/superpowers/specs/2026-07-19-factory-auto-improvement-loop-design.md` に、類似テーマの
既存設計ドキュメントが存在する（過去の別セッションの成果と見られ、本セッションの記憶には
無かった）。中身を確認したところ、**「マージ＝即昇格（シャドウ期間なし）、IssueAgentの
auto-okラベルによる無人自動マージ、実績監視による自動revert&pushロールバック」という、
本設計より踏み込んだ完全自動化方針**が既に合意されていた。ただし実装は一切着手されておらず
（`GENERATED_RULES`・`rollback_monitor.py`・関連CI いずれも未実装）、書かれただけで凍結された
状態だった。

本設計を進めるにあたりユーザーに確認したところ、**「人間のPRレビュー必須」という本設計の
方針を正式に採用し、旧ドキュメントの自動マージ・自動ロールバック方針は採らないことが確定した**。
旧ドキュメントは編集・削除せず経緯の記録として残すが、方針としては本ドキュメントが優先する。

一方、旧ドキュメントの調査で判明した以下の技術的事実は、昇格モデルによらず有効なため本設計にも
引き継ぐ:

**`src/backtest/rules/technical.py` と `src/rule_engine/rules/technical.py` は、ロジックがほぼ
同一の独立した重複実装であり、自動同期されていない**（diffで確認済み）。この構造のまま
新規ルールファイルをどちらか一方に追加するだけでは、「バックテストは通るが本番シグナルには
反映されない」あるいはその逆という事態になる。本設計では、Claude生成ルールに限り両者が
参照する共有レジストリ（`GENERATED_RULES`）を新設することでこれを解決する（既存6ルールの
重複自体は本設計のスコープ外、既存の技術的負債として現状維持）。

## アーキテクチャ全体

新規コンポーネント3つ + 1レジストリ:

1. **`src/backtest/claude_rule_generator.py`** — Claudeに新しい `TradingRule` サブクラスを
   書かせ、機械的な失敗（後述）に限り修復リトライさせる
2. **`src/backtest/sandbox_executor.py`** — AST静的検査 → Dockerサンドボックスでのバックテスト
   実行 → 結果を既存の `FactoryEvaluation` 互換形式で返す
3. **`src/rule_engine/generated_rules.py`**（新規、旧ドキュメントの設計を踏襲） —
   `GENERATED_RULES: dict[str, TradingRule]`。人間がマージしたPRがここに1エントリを追加する。
   `backtest/factory.py` の仮説評価と `rule_engine/pipeline.py` の `_RULE_INSTANCES` の**両方**が
   このレジストリを合成して参照するよう拡張する。これにより、PRマージの瞬間に「バックテストで
   検証されたのと同じコード」が本番シグナル生成でも使われることが保証される

```
[夜間バッチ（既存戦略ファクトリーに相乗り）]
  → claude_rule_generator: Claudeが候補コードをN件生成（既定3件/夜、設定可能）
  → sandbox_executor: AST静的検査
       ├─ 違反 → 違反箇所を添えてClaudeに再依頼（機械的失敗の修復ループ、後述）
       └─ 通過 → Dockerサンドボックスでバックテスト実行
            ├─ 実行時例外 → トレースバックを添えて再依頼（同じ修復ループ）
            └─ 正常完了 → 既存ゲート判定（Sharpe/DSR/PBO/窓別リターン/#372ガード）
                 ├─ 不合格 → 修復ループには回さず終了（ログのみ）
                 └─ 合格 → 既存 hypothesis_review.py（Claude批評、既定無効・助言のみ）
                      → GitHub Issue起票（既存 [factory:<hash>] パターン流用）
                      → 人間がレビューし、承認する場合はPRを作成
                           （生成コードを新ファイルとして追加 + GENERATED_RULES へ登録）
                      → 人間がPRをマージして初めて本番反映
```

## データアクセス範囲（MVP）

`generate_signal(df)` が受け取る `df` は既存ルールと同一の内容に揃える:

- 単一銘柄OHLCV（Open/High/Low/Close/Volume）
- 日次テクニカル指標 約19列（MACD系3・EMA fast/slow・ATR・RSI・ボリンジャーバンド4・
  ストキャスティクス2・OBV・出来高系3・カレンダー系3）
- 週足・月足マルチタイムフレーム特徴量（`w_`/`m_` 接頭辞、各5列）

マクロ/クロスアセット/センチメント特徴量、他銘柄比較は含めない（理由は前述のスコープ外節）。

## 安全機構

**AST静的検査（`sandbox_executor.py` の一次フィルタ）**: execする前に構文木を走査し、
`import os`/`import subprocess`/`import socket`/`__import__`/ネットワーク系ライブラリ/
`open(`/`eval(`/`exec(`/`compile(` を拒否する。許可ライブラリは `pandas`/`numpy`/`ta` 程度に
絞る。これは早期に明らかな不正コードを弾く高速フィルタであり、**主たる安全境界ではない**
（迂回可能なため過信しない）。

**Dockerサンドボックスの実行条件**（主たる安全境界）:
- `--network none`（外部通信不可）
- `.env`・`DATABASE_URL`をマウント/注入しない
- OHLCVデータのみ読み取り専用でマウント
- CPU/メモリ/実行時間の上限
- 結果はstdout経由でのみ親プロセスに返す（書き込み可能なボリューム共有なし）
- 既存の `stockfixer` イメージを流用し、`scripts/sandbox_evaluate_rule.py`（新規）が
  生成クラスの読み込み・`TradingRule`プロトコル適合検証・シグナル計算・結果出力を担う

**PIT安全性**: 生成コード固有の新しいリスクではなく、既存バックテストハーネスが窓ごとに
区切った `df` しか渡さない仕組みをそのまま継承する（生成コードが未来を覗く構造的な手段が無い）。

## 修復ループ（機械的失敗のみ）

**リトライしてよい失敗**:
- AST静的検査での拒否 → 違反箇所（禁止シンボル名・該当行）を添えて再依頼
- サンドボックス実行時の例外（クラッシュ） → トレースバックを添えて再依頼
- Claude応答のJSON形式不正 → スキーマ違反を添えて再依頼

これらは同じ修復予算を共有し、初回生成＋最大2回の修復（候補1件あたり最大3回のClaude呼び出し）
に制限する。

**リトライしてはならない失敗**:
- 静的検査・実行は正常に通ったが、DSR/PBO等のゲートに不合格だった場合。これは「バグ」では
  なく「単に良いルールではなかった」という正当な判定結果である。ここに修復ループを回すと、
  ゲートが「合否判定」から「Claudeが打ち勝つべき最適化対象」に変わり、戦略ファクトリー全体が
  過学習対策として作り込んできたものを自ら壊すことになる（バックテストの数字に勝つまで
  書き直す＝典型的なp-hacking）。ゲート不合格は一発勝負で終了する。

## 運用制御

- 既定は無効（`FACTORY_CLAUDE_RULEGEN_ENABLED=False`、`hypothesis_review.py` と同じ安全側既定）
- 1晩あたりの生成数を絞る（既定3件、設定可能）
- `LLM_BACKEND=cli`（サブスク課金、`src/quality/` BCと同じ方針）でAPIコスト青天井を回避

## 昇格フロー（人間レビュー必須）

1. ゲート合格 → GitHub Issue起票（既存 `[factory:<hash>]` パターン流用、`strategy-factory`
   ラベル。**`auto-ok` は付与しない** — これがIssueAgentの無人自動マージ対象から除外する
   唯一かつ確実な境界線）
2. 人間がIssueをレビューし、採用する場合はPRを作成する（生成コードを
   `src/rule_engine/rules/generated/` 配下等の新ファイルとして追加し、`GENERATED_RULES`
   レジストリへ1エントリ登録する変更を含む）
3. 通常のCI（既存 lint/unit-test/integration-test等）が通り、人間がレビュー・承認してマージ
4. マージされた瞬間、`GENERATED_RULES` を介して `backtest/factory.py` と
   `rule_engine/pipeline.py` の両方が同じコードを参照するようになり、次回の週次評価
   （`rule_selector.py`）以降で本番シグナル生成の候補に入る

## データ保存

新テーブル `factory_generated_rules`（既存 `factory_runs`/`strategy_promotions` と対で新設）:

| カラム | 説明 |
|---|---|
| `hypothesis_hash` | `source_code` のハッシュ（主キー） |
| `rule_name` | Claude提案のルール名 |
| `description` | 説明文 |
| `source_code` | 生成コード全文（verbatim保存。spec dictと違い決定的に再構築できないため必須） |
| `static_check_passed` | AST検査結果 |
| `gate_passed` | ゲート判定結果 |
| `issue_number` | 起票されたGitHub Issue番号 |
| `pr_number` | 採用PR番号（未採用ならNULL） |
| `promoted` | マージ済みか |
| `generated_at` | 生成日時（UTC） |

> JSON シリアライズ可能な dict であるため、実際には既存 `factory_runs` テーブルの
> `spec_json` カラムをそのまま再利用している。詳細は実装計画の Global Constraints
> セクション（`docs/superpowers/plans/2026-07-22-claude-rule-generation.md`）を参照。

## エラーハンドリング

- サンドボックス自体の起動失敗・タイムアウト（コード起因でなくインフラ起因） → 修復予算を
  消費せず候補をスキップしログのみ。1晩の候補が軒並みインフラ起因で落ちた場合は「良いルールが
  無かった」と区別してDiscord報告
- Claude呼び出し自体の失敗（レート制限・タイムアウト） → 既存 `claude_agent.py`/
  `quality/test_gap_review.py` と同じ規約でバックオフ再試行後、その晩の生成を諦め次回へ持ち越す
  （graceful degradation、既存パラメータ探索型の夜間バッチは影響を受けず継続）

## テスト戦略

- 単体: AST検査の許可/拒否リスト（危険な構文を含むサンプル・安全なサンプル双方）、
  `source_code` のハッシュ計算、Claude応答JSONのスキーマ検証、修復プロンプト組み立て
- 単体: `GENERATED_RULES` が空の状態で `backtest/factory.py`・`rule_engine/pipeline.py` が
  既存6ルールに対して従来通り動作すること（回帰なし）、ダミーエントリ登録時に両方から同一
  インスタンスが参照できること
- 結合: サンドボックス実行器に「正常に動くルール」「例外を投げるルール」「禁止import入り
  ルール」の3種のfixtureを通し、それぞれ期待通りの経路（成功/トレースバック返却/AST検査で
  即拒否）を辿ることを確認。Docker依存のテストは既存の統合テスト同様、Docker不可時はスキップ
