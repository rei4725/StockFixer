# バックテストによる暫定昇格（予想の改善のループを日の単位で回す）

日付: 2026-11-03 / 状態: 設計（人間の承認待ち）

## 1. なぜ

予想の改善のループ（ai-company の開発部が実験 E-NNN を出し、challenger が production に勝てば昇格する）は、仕組みはそろったが、実際には回っていない。

- production の統合モデルは 2026-04-11 に学習したもののままである。その後に特徴量の作り方が変わり（ATR #1240、除く列 #816 など）、今のコードと合わない。予想の 99% が「上がる」で、大きさは実際の約4倍になっている（Issue 1309、E-002）
- production が替わるのは週次学習（`python/src/orchestration/jobs/weekly_training.py`）の昇格ゲートだけである。challenger は週1回しか学習しないため、影の比べに使えるのは実質3〜5日しかない。そのため実験1本の結果が出るまで1〜2週かかる（E-001 は 10-29 にマージしたが、結果は 11-10）
- 昇格ゲート（`python/src/prediction/promotion_gate.py`）が載せている Walk-Forward の比べは、WF の要約に `model_name` の列が無いため判定から外れている（#1269）。実際に効いているのは、影の数日分の向きの的中率だけである。この物差しは、全部「上がる」と言うだけのモデルでも上げ相場では通ってしまう

人間の望み（2026-11-03）: 修正したモデルを**バックテストで評価して、暫定的に本番へ入れたい**。入れ替えるかどうかは **AI が自分で決めてよい**。

## 2. 何を作るか（ひとことで）

学習に**締め日**を足す。締め日より後の直近数週間を学習に使わずに取っておき、その期間で「修正したコードで学習した候補」と「今の production」を同じ予想の道で比べる。候補が勝てば、会社の人手を介さずに production を暫定で入れ替える。入れ替えた後は本番の成績を見張り、悪ければ自動で元に戻す。

## 3. 目標・やらないこと・失敗とみなすもの

### 目標
- 実験の PR がデプロイされてから、候補の評価と入れ替えの判断が出るまでを**1日以内**にする（今は1〜2週）
- 勝ち負けを**相場の向きに左右されない物差し**で決める
- 入れ替えも元に戻すのも人の手を要さず、何が起きたかが Discord と結果の JSON で後から追える

### やらないこと
- 本物の口座（`live_trading`）や売買のルールには触れない
- 今の週次の challenger の学習・影の比べ・昇格ゲートは消さず、そのまま並べて動かす（ゲートの基準を変える話は Issue 1309 の3番として別の PR で扱う）
- モデルの作り（特徴量・ハイパーパラメータ）は変えない。それは E-NNN の実験の側の仕事である
- 銘柄別のモデル（`StockXGBoostModel` など）は対象にしない。統合モデルだけを扱う

### 失敗とみなすもの（動いていても失敗）
- **取っておいた期間の情報が学習に漏れて**、バックテストだけ良く見える。この設計で一番の要所である（§5.1）
- バックテストで再現した production の予想が、実際に記録された production の予想と合わない（予想の道がずれていれば、比べ自体が意味を持たない）
- 入れ替えや元に戻すことが、通知も記録も無く黙って起きる
- 失敗した評価（データが読めない、学習が落ちたなど）を「候補の負け」や「候補の勝ち」として扱う

## 4. 決まっていること

| 項目 | 決めたこと | 誰の決定か |
|---|---|---|
| 評価の方法 | 締め日つきで学習し、取っておいた期間で候補と production を比べる | 人間 |
| 入れ替えの判断 | AI（コードのルール）が自分で行い、人の承認は要らない | 人間 |
| 取っておく期間 | 直近 **20 営業日** | Claude の判断 |
| 勝ちの条件 | §5.3 の3つの物差しで**すべて**上回ること | Claude の判断 |
| 入れ替えるモデル | **バックテストで測ったそのもの**（締め日つきで学習したもの）。全期間で学び直したものは入れない。測ったものと違うものを本番に出さないため。古さは最大で4週ほどだが、今の production の7か月に比べれば小さい | Claude の判断 |
| 元に戻す仕組み | 既存の `promote_unified_challenger()` が取る写し（`<本番の名前>_YYYYMMDD_HHMMSS.joblib`）を使う | Claude の判断 |
| 元に戻す条件 | §5.5 | Claude の判断 |

## 5. しくみ

### 5.1 締め日つきの学習（漏れを防ぐ）

`train_unified_model()`（`python/src/prediction/unified_model_pipeline.py`）に、締め日の引数（例: `train_end_date`）を足す。省略したときの振る舞いは今と同じにする。

締め日を渡したときは、**目的変数が締め日より後の値を使う行**をすべて学習から外す。horizon=1 なら、`date < 締め日` の行のうち、翌営業日の値が締め日以降になる行も外す。次のものは、すべて締め日より前の行だけで決める。

- 学習と検証の分け方（`_split_train_val_by_date`）。早く止める判断にも、取っておいた期間を使わない
- 特徴量の選び方（`_compute_and_save_unified_feature_selection`。今は X 全体を使っている）
- 除く列・正規化など、データ全体から値を決める処理（ほかにもあるかは、組む人が洗い出す）

`stock_features` の特徴量そのものが未来の値を使っていないか（中心化した移動平均、全期間で決めた正規化など）も、組む人が確かめる。使っているものがあれば、この設計の範囲で直すか、少なくとも結果の JSON に「漏れの恐れあり」と書いて自動の入れ替えを止める。

**漏れの検査を必ず入れる**: 単体テストとして、締め日以降の目的変数に目印の値を入れたデータで学習し、モデルにも分け方にも特徴量の選び方にもその値が効かないことを確かめる。

### 5.2 取っておいた期間での比べ

1. 締め日 = 今日から数えて 20 営業日前とする（jp と us の営業日の違いは、組む人が扱いを決める）
2. 候補 = 今の `develop` のコードで、締め日つきで学習した XGBoost と LightGBM。`UnifiedStockXGBoost_candidate` などの別名で保存し、challenger と production のファイルには触れない
3. 取っておいた 20 営業日の各日・各銘柄について、**本番の予想と同じ道**（`predict_unified.py` の特徴量のそろえ方、ATR のクリップ、モデルの組み合わせ方）で、候補と今の production の予想を作る。予想の道は分岐させず、同じ関数をデータの日付を指定して呼べるようにする
4. 予想を `actual_ratio` と突き合わせ、`baseline_metrics()`（`python/src/prediction/baseline_metrics.py`）で物差しを出す
5. **道の一致の検査**: 最新の日について、3 の道で作った production の予想と、本番の予想の関数（`predict_with_unified_model`）が同じ特徴量・同じモデル・同じ重みで出す予想を比べる。全銘柄で一致しなければ（浮動小数の誤差は除く）、比べが成り立たないとして入れ替えを止め、その旨を記録する（Claude の判断）
   - `prediction_accuracy` に記録された過去の production の予想との突き合わせは、**参考として JSON に書くだけ**にし、合否には使わない。`stock_features` は毎回、今のコードで作り直される（`market_data/pipeline.py` の `delete_stock_features`）。一方、取っておく期間には特徴量のコードの変更（ATR の直し e7c63ff5 など）が入っている。そのため、過去に記録された予想は今の特徴量からは再現できないからである
6. **アンサンブルの重み**: 本番は XGBoost と LightGBM の重みを `load_model_weights()` で DB から引く。バックテストでは次のように扱う（Claude の判断）
   - production には、今の DB の重みをそのまま使う（本番で実際に使っている重みだからである）
   - 候補には、入れ替えた後に本番で使われるのと同じ重みを使う
   - 入れ替えの時に、その重みが本番で使われるようにする（production の名前の metrics を書く、重みを固定して持つ、など）。作りは組む人に任せるが、「バックテストで使った重み」と「入れ替えた直後の本番の重み」が同じであることをテストで確かめる。使った重みは結果の JSON に書く

### 5.3 勝ちの条件（相場の向きに左右されない物差し）

候補が production に対して、次の3つを**すべて**満たすこと。

| 物差し | 条件 |
|---|---|
| `hit_rate_minus_majority`（的中率 − 常に多い方を言った場合の的中率） | 候補 > production |
| `mae` | 候補 < production |
| `rank_corr`（予想と実際の順位相関） | 候補 > production、かつ候補 > 0 |

さらに、件数が足りること（各モデルで `n_baseline` が 20 営業日 × 対象銘柄の 80% 以上）を求める。向きだけの的中率は記録はするが、勝ち負けには使わない。

ノイズで勝つことを避けるため、日ごとに `hit_rate_minus_majority` の差を出した表も結果に残す。日ごとの勝ち越しが過半数に満たない場合は勝ちにしない（Claude の判断）。

### 5.4 暫定の入れ替え

勝ったときは次の順で進める。

1. 今の production のファイルを写す。既存の写し方を流用し、`promote_unified_challenger()` と同じ形の写しの名前にする
2. 候補のファイルを production の名前で置く
3. 結果の JSON に、入れ替えた事実と写しのパスを書く
4. Discord で知らせる

次の予想の回からは、新しい production が使われる。今のキャッシュ（`get_cached_model` は mtime で読み直す）で足りるかは、組む人が確かめる。

入れ替えた日付と、そのとき戻せる写しは、状態のファイル（例: `results/backtest_promotion/state.json`）に1つだけ持つ。入れ替えが続いたときに、どこへ戻すかで迷わないためである。

### 5.5 入れ替えた後の見張りと、元に戻すこと

入れ替えた後、本番の予想で採点が済んだ日が **5 営業日**たまったら、1回判定する（数字は Claude の判断）。

- 新しい production の5日分の `hit_rate_minus_majority` が、バックテストで出た候補の値より **0.03 以上**低い
- または `rank_corr` が 0 以下
- または `predicted_up_rate` が 0.9 を超えるか 0.1 を下回る（全部が同じ向き、という今の病気がぶり返した）

このどれかに当たっても、**戻す先のほうが良いと言えるときだけ**戻す。戻す先（入れ替える前の production）の、バックテストでの `hit_rate_minus_majority` と `rank_corr` を、新しい production の5日分の値と比べる。戻す先が両方で上回るときに限り戻す（Claude の判断）。今の production は「99% が上がる」という病気を持っているため、条件に当たったというだけで戻すと、もっと悪いものに戻り得るからである。戻さなかったときは「条件に当たったが戻す先も悪い」と Discord と JSON に書き、次の実験に任せる。

戻すときは、写しから元の production に戻し、Discord と JSON に書く。戻した候補と同じコードの版からは、もう一度入れ替えない（行ったり来たりを防ぐ）。

5日で判定した後は見張りを終える。その後は通常の週次の影の比べに任せる。

### 5.6 いつ動くか

- スケジューラ（`python/src/orchestration/scheduler.py`）のジョブとして、**予想のコードの版が前回のバックテストから変わった日**の夜間（市場が閉まっている時間で、週次学習と重ならない時間）に1回動く。同じ版での再実行はしない
- 手で動かす入口（CLI か `python -m ...`）も置く。会社の CEO や人間がログを見て再実行できるようにするためである
- 1日1回までとする。学習2本で 8GB の上限に近い（#807）ため、ほかの重いジョブと同時には動かさない

「予想のコードの版」の決め方（VERSION、学習と予想に関わるファイルのハッシュなど）は組む人に任せる。

### 5.7 記録と通知

- `results/backtest_promotion/YYYYMMDD_HHMMSS.json` に、締め日、期間、件数、各モデルの物差し、日ごとの差、道の一致の検査の結果、勝ち負けとその理由、入れ替えたか、写しのパスを書く。ai-company の CEO はこれを読んで台帳（`state/dev/prediction-experiments.md`）を書く
- Discord には、評価の結果（勝ち／負け／比べが成り立たない）、入れ替え、元に戻したことを、それぞれ1通ずつ送る
- 失敗（学習の例外、データが空など）は「負け」にせず、失敗として JSON と Discord に出す（#1295 と同じ考え方）

## 6. 週次の流れとの関係

- 週次の challenger の学習・影の比べ・昇格ゲートはそのまま動かす。暫定で入れた production も、週次の流れでは普通の production として扱う
- 週次の昇格と暫定の入れ替えが同じ日に起きないよう、どちらか一方が動いている間はもう一方を待たせる（排他の仕方は組む人に任せる）
- 見張りの5日の間に週次の昇格が起きた場合は、見張りをやめる。戻す先が分からなくなるためである

## 7. 確かめ方

- 単体テスト: 漏れの検査（§5.1）。勝ちの条件の判定。全部「上がる」と言う予想の列では `hit_rate_minus_majority` が 0 付近になり、勝てないこと。元に戻す条件の判定。失敗を負けにしないこと
- 結合の確かめ: 本番のデータで手で1回動かし、道の一致の検査が通ること、結果の JSON が書かれること、入れ替えたときに写しから戻せることを、dry_run と実際の入れ替えの両方で確かめる
- 最初の本番の回は、今の production が壊れているため、ほぼ確実に入れ替えになる見込みである。その後5日の見張りが正しく判定するかを確かめる

## 8. 組む人に任せること
