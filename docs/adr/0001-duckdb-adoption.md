# ADR-0001: DuckDB 採用

- **日付**: 2024-01-01
- **ステータス**: Accepted
- **Roadmap ID**: NF-503

## コンテキスト

StockFixer では、株価特徴量・予測結果・ペーパートレード履歴を永続化するデータベースが必要だった。
Docker コンテナ上で動作し、外部サーバーを持たない単一プロセス（スケジューラー＋API サーバー）が
メインの運用形態であるため、セットアップの簡便さとファイルシステムへの親和性が重要な制約となった。

## 検討した選択肢

| 選択肢 | 概要 |
|--------|------|
| DuckDB | 組み込み列指向 OLAP DB。外部サーバー不要、ファイル 1 本で完結 |
| PostgreSQL | 広く使われる RDBMS。別コンテナが必要、運用コスト高 |
| SQLite | 組み込み行指向 DB。大量カラムの SELECT が遅く、Pandas 連携も煩雑 |

## 決定内容

DuckDB を採用する。

## 理由

- **外部依存ゼロ**: ファイル 1 本（`stockfixer.duckdb`）で動作し、Docker Compose に DB コンテナを追加しなくてよい。
- **Pandas 相互運用**: `con.execute("SELECT ...").fetchdf()` で直接 `pd.DataFrame` を取得でき、特徴量・予測結果の読み書きコードが簡潔になる。
- **列指向の SELECT 性能**: `stock_features` テーブルは行数×カラム数が多く、特定カラムのみを SELECT するケースが多い。DuckDB の列指向ストレージはこのワークロードに適している。
- **PostgreSQL を採用しない理由**: 別コンテナが必要で Docker Compose の複雑度が増す。今フェーズのデータ量（数万〜数十万行）では OLTP 性能は不要。
- **SQLite を採用しない理由**: 行指向ストレージのため大量カラムを持つ特徴量テーブルの全カラム SELECT が遅い。また `fetchdf()` 相当の API がなく変換コードが増える。

## 結果

**正の効果**:
- セットアップが `pip install duckdb` のみで完結する。
- 特徴量・予測結果の読み書きコードが Pandas-native で書ける。
- Docker 環境でのデプロイが単純（DB コンテナなし）。

**負の効果（トレードオフ）**:
- 読み書き接続はプロセスレベルで 1 本しか持てない（→ ADR-0002 で対処）。
- 複数プロセスから並行書き込みを行うとロック衝突が発生する（→ ADR-0002 で対処）。
- スケールアウト（シャーディング等）が困難なため、データ量が数億行を超えた場合は移行が必要。
