# ADR-0002: DuckDB 短命接続（short-lived connection）パターン採用

- **日付**: 2024-03-01
- **ステータス**: Accepted
- **Roadmap ID**: NF-503

## コンテキスト

DuckDB（ADR-0001）は読み書き接続をプロセスレベルで 1 本しか許可しない。
StockFixer の Docker 環境ではスケジューラー（APScheduler）と Flask API サーバーが同一コンテナ内で
複数スレッドとして動作しており、長寿命の接続を保持すると他スレッド・他プロセスからの
アクセスが `IOException` でブロックされる問題が発生した。

## 検討した選択肢

| 選択肢 | 概要 |
|--------|------|
| シングルトン長寿命接続 | 起動時に 1 本の接続を作成し使い回す |
| 短命接続（コンテキストマネージャー） | DB 操作ごとに接続を開き、終了後すぐ閉じる |
| 接続プール | 複数接続を事前生成してプールする |

## 決定内容

`_db_connection()` コンテキストマネージャーによる短命接続パターンを採用し、
プロセス間排他制御には `filelock` を使用する。

## 理由

- **シングルトン長寿命接続を採用しない理由**: DuckDB の読み書き接続は 1 プロセスに 1 本の制限があり、
  長寿命で保持すると他スレッドや他プロセスからの接続が失敗する。
  スケジューラーと API サーバーが並行動作する環境では根本的に機能しない。
- **接続プールを採用しない理由**: DuckDB は SQLAlchemy のような標準プールに対応していない。
  独自プールを実装しても結局「同時に 1 接続のみ」という制約は変わらず、実装が複雑になるだけ。
- **短命接続を採用する理由**:
  - `with _db_connection() as con:` の構文で接続の開閉を宣言的に書ける。
  - `finally` ブロックで確実に `con.close()` が呼ばれ、ロックが残留しない。
  - `FileLock` でプロセス間排他を保証し、ロック衝突時は最大 10 回リトライする。
  - 読み取り専用アクセスには `get_readonly_connection()` を提供し、書き込みロックを取らずに並行 SELECT できる。

## 結果

**正の効果**:
- スケジューラー・API サーバーが並行動作しても DB ロック衝突が発生しない。
- `with` ブロックを外れると自動的に接続が閉じられ、ロック残留バグを防ぐ。
- 読み取り専用接続（`get_readonly_connection()`）により SELECT 側は書き込みロックを取らずに動作できる。

**負の効果（トレードオフ）**:
- 1 回の DB 操作ごとに接続の開閉オーバーヘッドが発生する。
  （DuckDB のファイルオープンは軽量なため実用上は問題ない）
- 複数のテーブルにまたがるトランザクションは `_db_connection()` の 1 つの `with` ブロックに収める必要があり、
  コードの局所性を意識した設計が必要。
- **DuckDB 並行書き込み禁止**: DB 書き込みは必ず逐次実行すること。複数スレッドから同時に
  `_db_connection()` を呼び出すと `FileLock` により直列化される。
